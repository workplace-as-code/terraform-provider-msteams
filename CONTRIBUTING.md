# Contributing

Thank you for your interest in contributing to the Terraform provider for Microsoft Teams.

## How to Contribute

### Reporting Bugs
Open an issue using the [bug report template](.github/ISSUE_TEMPLATE/bug_report.md).

### Requesting a New Resource
Open an issue using the [new resource template](.github/ISSUE_TEMPLATE/new_resource.md).

### Submitting Code

1. Fork the repository
2. Create a feature branch: `git checkout -b feat/msteams_my_resource`
3. Make your changes
4. Run tests: `make test`, then `test/run.sh` against a test tenant (see the script header for the required `TEAMS_*` variables).
5. Format code: `make fmt`
6. Regenerate the documentation: `make docs` (never edit `docs/` by hand)
7. Submit a pull request

## Development Setup

### Requirements
- Go 1.25+ (see `go.mod`)
- PowerShell 7+ (`pwsh`)
- MicrosoftTeams PowerShell module
- A Microsoft 365 developer tenant (for acceptance tests)

### Local Installation
```bash
git clone https://github.com/workplace-as-code/terraform-provider-msteams
cd terraform-provider-msteams
make install
```

## Adding a New Resource

A new policy or configuration type only needs an entry in `internal/resources/specs.go`: the generic resource and `bridge/scripts/cs_object.ps1` handle it. Check the parameter names with `(Get-Command Set-Cs<noun>).Parameters` first. Other resources:

1. Create `internal/resources/my_resource.go`
2. Create `bridge/scripts/my_resource.ps1` (embedded automatically at build time)
3. Register it in `internal/resources/registry.go`, with the `Get-` cmdlet noun that lists its objects (`terraform query`)
4. Add the example `examples/resources/msteams_my_resource/resource.tf` (no `terraform` or `provider` block) and the import examples `import.sh`, `import-by-string-id.tf` and `import-by-identity.tf` next to it
5. Add the page template `templates/resources/my_resource.md.tmpl` (copy an existing one: it sets the menu category, the permissions and the Microsoft documentation links), then run `make docs` and `make examples`

### Documentation

`docs/` is generated by [tfplugindocs](https://github.com/hashicorp/terraform-plugin-docs) from the provider schema (attribute descriptions live in the Go code), `templates/` and `examples/`: run `make docs` after changing any of them. CI fails when `docs/` is out of date. Guides are written in `templates/guides/` and copied as is.

### Bridge script contract

Every script must follow the same output contract, otherwise Terraform state can be lost:

- Success: one JSON object on stdout, exit code 0.
- `Get` on an object that does not exist: empty stdout, exit code 0. This is the only case where the provider removes a resource from state.
- Any other failure (authentication, throttling, invalid input): message on stderr, non-zero exit code. Never swallow errors with `-ErrorAction SilentlyContinue` on write operations.

Scripts normally run inside a long-lived PowerShell process (`bridge/scripts/bridge_host.ps1`) that serves many requests and keeps the Teams connection opened by `auth.ps1`. Each script runs in its own scope, so plain variables are safe. Never store state in `$global:` variables or rely on anything left over from a previous request (the only exception is the connection flag set by `auth.ps1`). Write results with `Write-Output` and errors with `[Console]::Error.WriteLine` or `throw`: the host captures both per request. Set `TEAMS_BRIDGE_MODE=oneshot` to run each script in its own process while debugging.

Send only the attributes set in the Terraform configuration (the `put*` helpers in `internal/resources/helpers.go`) and build cmdlet parameters with `ConvertTo-BridgeSplat` from `common.ps1`. Unset attributes then keep their Teams value instead of a default chosen by the provider. `internal/client/scripts_test.go` runs the scripts against stubbed Teams cmdlets: extend it when you add a script.

Secrets reach `auth.ps1` through environment variables, never through parameters. To test a script change without rebuilding the provider, point `TEAMS_BRIDGE_DIR` at your local `bridge/scripts` folder.

## Commit Convention

We use [Conventional Commits](https://www.conventionalcommits.org/). Pull requests are squash-merged, so the pull request title becomes the commit message, and then a line of the release notes: write it for the people who use the provider.

```
feat: add msteams_meeting_policy resource
fix: handle missing messaging policy gracefully
docs: update authentication guide
chore: bump terraform-plugin-framework to 1.6.0
```

## Releasing

For maintainers. Each step goes through a pull request, except the tag.

1. Run `test/run.sh` against the test tenant from the code of `main` (see the script header for the variables) and wait for it to pass.
2. Note the versions it ran with, and copy them into the tested versions table of `templates/index.md.tmpl`, then run `make docs`:

   ```bash
   terraform version
   pwsh -NoProfile -Command '$PSVersionTable.PSVersion; Get-Module -ListAvailable MicrosoftTeams | Select-Object Name, Version'
   ```

3. Merge the pull request, then tag `main` and push the tag:

   ```bash
   git switch main && git pull --ff-only
   git tag v0.1.2
   git push origin v0.1.2
   ```

4. The **Release** workflow builds, signs and publishes the release, with release notes generated from the titles of the pull requests merged since the previous tag (`feat` → Features, `fix` → Bug fixes, `docs` → Documentation; `release`, `ci` and `test` are left out). Read them on the release page and edit them there if needed. Check that the Terraform Registry shows the new version a few minutes later.
